# Data Engineering — Week 1 Topics


## What is Data Engineering?

**Data Engineering** is the work of building and maintaining systems that collect, move, transform, store, and prepare data so that other people, applications, and business teams can use it reliably.

A simple way to understand Data Engineering is to think of a company as an organization where many systems generate data. The Data Engineer builds the **data highway** that moves this data from its source to the people and systems that need it.

```text
Applications
    ↓
Customers / Employees / Systems generate data
    ↓
Data Engineers collect the data
    ↓
Data Engineers clean and transform the data
    ↓
Data is stored
    ↓
Analysts / Data Scientists / Business teams use it
    ↓
Reports / ML models / Business decisions
```

---

# 1. Data Engineering vs Software Development vs Data Science vs Analytics


Imagine an e-commerce company. A customer places an order, and the following flow occurs:

```text
Customer → Website → Order → Database → Data Platform → Report
```

Different professionals are responsible for different parts of this process.

## 1.1 Software Developer

A Software Developer builds the **application** that customers or employees interact with.

Examples:

- Login system
- Shopping cart
- Payment functionality
- Order API
- Product search
- Mobile application

Their main question is:

> **How do I build a reliable application that performs a business function?**

Example:

```python
def create_order(customer_id, product_id):
    # Validate the order
    # Process payment
    # Update inventory
    # Create order
    pass
```

---

## 1.2 Data Engineer

A Data Engineer makes sure the data generated by applications can be **collected, processed, stored, and made available**.

For example:

```text
Application Database
       ↓
Extract Data
       ↓
Transform / Validate
       ↓
Data Warehouse
       ↓
Analytics Tables
```

Their main question is:

> **How do I reliably move and prepare this data so other teams can use it?**

---

## 1.3 Data Analyst

A Data Analyst uses prepared data to answer **business questions**.

Examples:

- How much revenue did we make last month?
- Which product sells the most?
- Which region has the highest customer growth?
- Why did sales increase or decrease?

Example SQL:

```sql
SELECT
    product_id,
    SUM(sales_amount) AS revenue
FROM sales
GROUP BY product_id;
```

The analyst may then create a dashboard using a BI tool.

---

## 1.4 Data Scientist

A Data Scientist uses data to identify patterns, make predictions, and build statistical or machine-learning models.

For example:

> Which customers are likely to stop using our application?

Typical flow:

```text
Customer Data
     ↓
Feature Engineering
     ↓
Machine Learning Model
     ↓
Churn Prediction
```

---

## 1.5 Quick Comparison

| Role | Main Question |
|---|---|
| Software Developer | How do we build the application? |
| Data Engineer | How do we move and prepare the data? |
| Data Analyst | What happened and why? |
| Data Scientist | What will happen / what can we predict? |

There is some overlap between these roles, but their **primary responsibilities are different**.

# 3. OLTP vs OLAP

This is a fundamental Data Engineering concept.

The easiest way to remember it is:

> **OLTP = Run the business**

> **OLAP = Analyze the business**

---

## 3.1 OLTP — Online Transaction Processing

OLTP systems handle day-to-day application transactions.

Imagine a customer buying a product.

The system may need to:

```text
Create Order
Update Payment
Update Inventory
Update Customer
```

These operations need to be:

- Fast
- Reliable
- Consistent
- Accurate

Typical OLTP databases include:

- PostgreSQL
- MySQL
- SQL Server
- Oracle

Example table:

```text
orders

order_id
customer_id
product_id
order_date
amount
status
```

Example query:

```sql
SELECT *
FROM orders
WHERE order_id = 10001;
```

This query is looking for a specific transaction quickly.

---

## 3.2 OLAP — Online Analytical Processing

OLAP systems are designed primarily for **analysis**.

Suppose management asks:

> What was our total revenue for each region over the last three years?

This could require processing millions or billions of records.

Typical flow:

```text
Orders
Customers
Products
Regions
Payments
     ↓
Data Warehouse
     ↓
Analytics
```

Typical OLAP technologies include:

- Snowflake
- BigQuery
- Amazon Redshift
- Databricks
- ClickHouse

Example:

```sql
SELECT
    region,
    SUM(revenue) AS total_revenue
FROM sales
GROUP BY region;
```

---

## 3.3 OLTP vs OLAP Comparison

| Feature | OLTP | OLAP |
|---|---|---|
| Purpose | Run applications | Analyze data |
| Users | Applications / customers | Analysts / business users |
| Queries | Small and frequent | Large and complex |
| Data | Current operational data | Historical / analytical data |
| Example | Order placement | Revenue analysis |
| Typical system | PostgreSQL | Snowflake |
| Optimization | Fast transactions | Fast analytical queries |

### Important Point

OLTP is not "old" and OLAP is not "new". They solve **different problems**.

A company may need both:

```text
                 Company
                    |
          ┌─────────┴─────────┐
          ↓                   ↓
       OLTP                OLAP
    Run business         Analyze business
          ↓                   ↑
       App DB             Warehouse
```

# 4. Batch vs Streaming

Data can be processed in different ways. Two major approaches are **Batch Processing** and **Streaming**.

---

## 4.1 Batch Processing

Batch processing means:

> Collect data for a period and process it together.

Example:

```text
12 AM
 ↓
Collect yesterday's data
 ↓
Process
 ↓
Load warehouse
```

For example, a company might process sales every night:

```text
Monday sales ─┐
Tuesday sales ├──→ Nightly Pipeline → Warehouse
Wednesday ────┤
Thursday ─────┤
Friday ───────┘
```

Common batch use cases:

- Daily reports
- Monthly financial reports
- Payroll
- Historical data processing
- Large ETL jobs
- Daily data warehouse loads

---

## 4.2 Streaming Processing

Streaming means:

> Process data continuously as it arrives.

Example:

```text
Customer Click
      ↓
Event
      ↓
Kafka
      ↓
Streaming Processing
      ↓
Dashboard / Database
```

For example, a fraud detection system may need to process a payment within seconds:

```text
Payment
   ↓
Event
   ↓
Stream Processing
   ↓
Fraud Model
   ↓
Risk Score
```

Common streaming technologies include:

- Apache Kafka
- Apache Flink
- Spark Structured Streaming
- Amazon Kinesis
- Google Pub/Sub

---

## 4.3 Batch vs Streaming — When to Use Which?

Do not think:

> Streaming is always better than batch.

Instead ask:

> **How quickly does the business need the data?**

### Use Batch When

Minutes, hours, or days of delay are acceptable.

Example:

> Generate yesterday's sales report every morning.

Batch processing is often simpler and cheaper.

### Use Streaming When

The business needs data almost immediately.

Examples:

- Fraud detection
- Real-time monitoring
- IoT monitoring
- Live dashboards
- Real-time recommendations
- Event processing

```text

Transform
```

```text

  ↓

  ↓

  ↓
```

Modern cloud data warehouses have powerful processing capabilities, so ELT is very common.

# 6. Data Engineer Responsibilities

A Data Engineer is not simply someone who writes Python and SQL.

Typical responsibilities include:

- Understanding business requirements
- Analyzing source systems
- Designing data pipelines
- Extracting and ingesting data
- Transforming data
- Building data models
- Writing SQL and Python
- Implementing data quality checks
- Scheduling and orchestrating pipelines
- Monitoring production pipelines
- Troubleshooting failures
- Managing incremental loads
- Handling schema changes
- Improving reliability and performance
- Supporting analytics and business teams

---

## 6.1 Requirement Understanding

Suppose a client says:

> "We need a sales dashboard."

A data engineer asks questions first.

For example:

```text
What is a sale?

Which system contains sales data?

What is the source database?

How frequently should data refresh?

Who will use the dashboard?

What does "revenue" mean?

Should cancelled orders be included?

What timezone should be used?

How much historical data is required?

What happens if the source is unavailable?
```

---

After understanding the requirement, the Data Engineer investigates the source system.

Example:

```text
PostgreSQL
    ↓

```

You might inspect the data using SQL:

```sql

FROM orders
LIMIT 100;
```

Check the row count:

```sql

FROM orders;
```

You may also investigate:

- Primary keys
- NULL values
- Duplicate records
- Data types
- Update timestamps
- Relationships
- Table size
- Historical data
- Source system constraints

## 6.7 Data Quality

Data quality is a major Data Engineering responsibility.

Imagine yesterday the dashboard showed:

```text
Revenue = $5 million
```

Today it shows:

```text
Revenue = $50 million
```

The business asks:

> "Why?"

One possible reason is that the pipeline loaded the same records twice.

Therefore, Data Engineers build checks such as:

```text
Are there duplicate IDs?
Are required fields NULL?
Did today's row count suddenly drop?
Are amounts negative?
Did the pipeline load today's data?
```

Example:

```sql
SELECT COUNT(*)
FROM orders
WHERE order_id IS NULL;
```

Expected result:

```text
0
```

The goal is not only to move data.

The goal is to move **correct and trustworthy data**.

---

## 6.8 Monitoring and Production Support

A production pipeline may normally run at:

```text
02:00 AM
```

But one day:

```text
02:15 → Running
02:30 → Running
03:00 → Failed
```

The dashboard may not contain fresh data.

A Data Engineer needs to:

```text
Detect failure
    ↓
Investigate logs
    ↓
Identify root cause
    ↓
Fix issue
    ↓
Rerun pipeline
    ↓
Validate data
```

Production support is a normal and important part of Data Engineering.

---

## 6.9 Incremental Loading

Suppose a database contains:

```text
1 billion orders
```

It is inefficient to copy all 1 billion rows every day.

Instead, we can process only new or updated records.

For example:

```text
Yesterday:
100 million records

Today:
50,000 new/updated records
```

A common approach is to use an `updated_at` timestamp:

```sql
SELECT *
FROM orders
WHERE updated_at > :last_successful_timestamp;
```

This is called **incremental loading**.

Benefits include:

- Lower processing time
- Lower cost
- Lower network usage
- Lower load on source databases
- Better pipeline performance

---

## 6.10 Reliability

A production pipeline should continue to work correctly even when problems occur.

Possible failures include:

```text
Network failure
API timeout
Bad records
Duplicate data
Source unavailable
Warehouse unavailable
Pipeline crash
Schema changes
```
> **"What happens when this fails?"**

A good production pipeline should have appropriate:

- Error handling
- Retries
- Logging
- Alerts
- Monitoring
- Data validation
- Recovery procedures

Reliability is one of the major differences between a simple script and a production data pipeline.

The most important concepts to understand are:

2. **Data Lifecycle** — understanding how data moves through an organization.
3. **OLTP vs OLAP** — understanding operational systems versus analytical systems.
4. **Batch vs Streaming** — choosing processing based on business latency requirements.
5. **Modern Data Stack** — understanding sources, ingestion, lakes, warehouses, transformation, and BI.
6. **ETL vs ELT** — understanding different data integration patterns.

Data Engineering sits between the systems that **generate data** and the people or applications that **use data**.
